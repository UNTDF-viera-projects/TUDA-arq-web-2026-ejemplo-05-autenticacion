01 · Ciclo de vida

La sesión vive en el servidor, su referencia en una cookie

  • Cliente: auth01_session, HttpOnly y duración configurada de ocho horas.
  • Servidor: sesión Django y usuario activo. Contraseña con hash Django.
  • Recarga: /me/ valida la sesión y devuelve la página.
  • Cierre del navegador: la cookie con Max-Age puede sobrevivir hasta vencer.
  • Vencimiento: volver al ingreso.
  • Salida: POST con CSRF invalida la sesión y limpia la cookie.

Una cookie persistente y una “cookie de sesión del navegador” no tienen el mismo ciclo de vida. La configuración determina esta duración.

02 · Ciclo de vida

React restaura el perfil, la cookie acredita la identidad

  • Cookie: auth02_session HttpOnly, ocho horas por configuración.
  • React: perfil e inscripciones solo en memoria.
  • Recarga: GET /api/v1/me con credentials include.
  • Cookie CSRF: auth02_csrf. El token llega por JSON.
  • Salida: POST /auth/logout con cookie y CSRF.
  • Vencimiento o 401: limpiar el área privada y pedir ingreso.

HttpOnly protege la lectura de la cookie. La protección CSRF y la validación de permisos siguen siendo necesarias.

03 · Ciclo de vida

sessionStorage conserva una contraseña reversible

  • Valor: Base64 de email:contraseña, clave auth03_basic.
  • Recarga: readCredential y /me antes del área privada.
  • Salida o 401: clearCredential borra storage y memoria.

  • Exposición: JavaScript y XSS pueden leerlo. Vaciar el input no lo borra.
  • Servidor: cambiar contraseña o desactivar cuenta invalida próximos requests.

04 · Ciclo de vida

Una recarga recupera el token y vuelve a verificarlo

  • Cliente: auth04_token en sessionStorage. JavaScript puede leerlo.
  • Recarga: leer token, GET /me, luego cargar inscripciones.
  • Duración: OPAQUE_SECONDS, una hora por defecto, sin renovación.
  • 401: eliminar la credencial y volver al ingreso.
  • Logout: revocar el hash en servidor y borrar copias locales.
  • Error de red al salir: la limpieza local no confirma la revocación remota.

Una pestaña no da seguridad frente a XSS. El hash en la base evita almacenar el secreto original, pero no impide usar un token robado y vigente.

05 · JWT

Un JWT firmado puede leerse

PAYLOAD DEL ACCESS
{
  "sub": "<id de usuario>",
  "iat": 1788541200,
  "exp": 1788541260,
  "iss": "untdf-demo",
  "type": "access"
}
  • header.payload.signature
  • sub identifica al usuario, no al participante.
  • iat y exp delimitan emisión y vencimiento.
  • iss y type se verifican junto a la firma.
  • La firma detecta alteraciones. El payload no contiene secretos.

PyJWT valida con el algoritmo permitido por el servidor. Un claim malformado debe producir 401, sin error interno.

05 · Ciclo de vida

La continuidad la aporta una cookie HttpOnly

  • Access: memoria, ACCESS_SECONDS, 60 segundos por defecto.
  • Refresh: auth05_refresh, REFRESH_SECONDS, siete días por defecto.
  • Cookie: HttpOnly, SameSite y Path /api/v1/auth/.
  • Recarga: obtener un access mediante refresh válido.
  • Cierre: la cookie persistente puede sobrevivir hasta vencer.
  • Logout: revoca refresh, borra cookie y memoria.

Un access ya emitido puede seguir funcionando después del logout, hasta su expiración. Esta implementación no mantiene una lista de revocación de access.

/me cancela una actividad del usuario actual

DOS CONTRATOS DIFERENTES
DELETE /api/v1/me/enrollments/{activity_id}
  Cancelar mi inscripción a esa actividad.

DELETE /api/v1/enrollments/{enrollment_id}
  Cancelar una inscripción identificada.
  Debe comprobar su propietario.
  • Obtener usuario del mecanismo de esta carpeta.
  • Buscar su participante en el backend.
  • Nunca aceptar un participant_id editable.
  • Un enrollment_id ajeno demuestra 403 forbidden.

El primer endpoint no borra inscripciones ajenas. Para demostrar un fallo de propiedad hay que usar el segundo y dos usuarios.

Contrato observable

Un error de autenticación no es un error de permisos

SituaciónResultadoEvidencia
Credencial ausente, inválida, vencida o revocada401 unauthorizedSe pide ingreso o se limpia el secreto local.
Inscripción de otra persona403 forbiddenLa identidad es válida, la operación no está permitida.
Cookie en escritura sin token CSRF válido403 (csrf_failed en 02 y 05)Falta prueba de contexto legítimo.
Sin cupo409 capacity_exhaustedRegla de dominio, no autenticación.
Origen fuera de la lista CORSError del navegador al leerNo equivale a un estado HTTP fijo.
/me/ HTML anónimo en 01302 al ingresoEl flujo entrega páginas y redirecciones.

Amenazas del navegador

XSS ejecuta código dentro de la aplicación

  • Puede leer Basic o token opaco de sessionStorage.
  • Puede usar el access mientras está en memoria.
  • Puede realizar acciones con cookies HttpOnly.
  • Puede leer datos visibles del usuario.
  • Escapar contenido y evitar HTML sin sanitizar.
  • Revisar dependencias y aplicar CSP según despliegue.
  • Reducir exposición y duración de secretos.
  • Mantener autorización en el servidor.

HttpOnly reduce el robo por lectura directa de la cookie. No impide todas las acciones de un script que ya ejecuta en el origen confiado.
